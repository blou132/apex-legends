# Phase16P - Real Dolphin interface lifecycle

## Executive result

Phase16P resolved the first real client-side Dolphin interface lifecycle. The
proven `DolphinCallback` table stores an owner pointer at `+0x08`; exact owner
methods identify that pointer as `DolphinUpdater` with probable confidence.
`DolphinUpdater::Shutdown` and `CheckUpdate` independently converge on a
persistent interface field at owner `+0x1f0`.

Four exact field readers are visible. Most importantly, the readable
`CheckUpdate` continuation loads `owner+0x1f0`, loads vtable slot `+0x10`, and
calls it at Ghidra `0x05b2f0ac` / ELF `0x05a2f0ac`. This is the known
`GCloudDolphinImp::Init` ABI slot. The client-side Init dispatch is now proven;
the concrete dynamic vptr remains probable because the acquisition writer is
not visible.

The exact `ReleaseDolphin` import was revalidated, but an exact branch scan
found zero direct callers. Shutdown instead physically calls the preceding
`DolphinHelper::GetCurApkPath` PLT after interface slot `+0x18`, then clears
`+0x1f0`. That mismatch is reported exactly and is not relabeled.

The non-null writer for `+0x1f0` lies in a protected or statically opaque
region. Acquisition mechanism and source therefore remain unknown. The dead
Phase16O `CreateDolphin` call was not reused.
